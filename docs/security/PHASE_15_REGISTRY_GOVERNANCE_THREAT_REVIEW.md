# Phase 15 — Registry Governance Threat Review

Reviews every item in the Phase 15 prompt's Section 134 checklist against the actual
implementation.

## Scope note: no automated source-fetch was built this phase

Sections 129-131 assume an automated source-health fetcher exists that fetches
admin-supplied `officialSourceUrl` values. **This phase did not build that fetcher** (Section 19's
"implement only if capacity supports it" — evaluated and deferred; see
`docs/registry/REGISTRY_REVERIFICATION_POLICY.md`'s "triggers" section). Confirmed by grep: no
code path in `apps/web/src` fetches `crawlers.officialSourceUrl` automatically — it is stored,
displayed, and used only as a link, never as a target the application itself requests. This
significantly narrows several threats below, and is disclosed as a scope limitation, not a
false "this doesn't apply" claim — if a future phase builds the fetcher, this document's SSRF
section must be revisited against real fetch code, not assumed safe by extension of this review.

## Threat-by-threat

| Threat                         | Status                                                                                                                                                                                                                             | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Malicious source URL           | **Mitigated by scope**                                                                                                                                                                                                             | `officialSourceUrl` is validated as a well-formed URL (`z.string().url()`) at every write path (`api/admin/registry/crawlers/index.ts`, `.../verify.ts`) but never fetched by the app — no SSRF surface exists yet. A malicious value can only ever be displayed as a link to an admin, who chooses whether to click it (same trust boundary as any external link shown in any admin tool).                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Compromised operator page      | **Out of scope this phase**                                                                                                                                                                                                        | No content from any `officialSourceUrl` is ever ingested or rendered by the app (no fetcher exists). If Section 19's source-health fetcher is built later, this becomes live risk requiring the safe-fetch chokepoint (`packages/scanner`, ADR-0005) exactly as CLAUDE.md requires for any customer/external-supplied URL fetch.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Source redirect hijack         | **Out of scope this phase**, same reasoning.                                                                                                                                                                                       |
| SSRF                           | **Not applicable this phase** — no fetch exists. Documented as a hard requirement for whoever builds the fetcher later: it must go through `packages/scanner`'s existing safe-fetch chokepoint, never a second bespoke fetch path. |
| Fake crawler submission        | **Mitigated**                                                                                                                                                                                                                      | Every crawler creation requires `requireAdminAction` (server-side Super Admin session + reason, audited). No public submission path exists.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Classification mistake         | **Mitigated by process, not code**                                                                                                                                                                                                 | `validateReleaseCandidate` catches structural mistakes (missing source, missing verification, duplicate token) but cannot catch a _wrong-but-well-formed_ classification — that is why Section 6's live-research discipline and `docs/registry/PHASE_15_FULL_SOURCE_REVERIFICATION_REPORT.md` exist as a process control, and why `docs/registry/REGISTRY_CORRECTION_WORKFLOW.md` exists for when mistakes are found later.                                                                                                                                                                                                                                                                                                                                                                                   |
| Unverified crawler publication | **Fixed this phase**                                                                                                                                                                                                               | `getActiveRegistry`/`resolveEvaluationRows` unconditionally excludes `unverified`/`retired` lifecycle from evaluation, regardless of what a release snapshot contains — verified by `registry-reproducibility.integration.test.ts` and `admin-registry.integration.test.ts`. `validateReleaseCandidate` additionally requires a verification date for every evaluation-eligible entry.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Release tampering              | **Mitigated**                                                                                                                                                                                                                      | `registry_version_entries.snapshot` is written once at `createRegistryRelease` time and never updated by any code path after that (grepped — no `UPDATE registry_version_entries` exists anywhere in the codebase). A published release's checksum is stored and independently re-verifiable via `pnpm registry:checksum:verify`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Checksum mismatch              | **Detectable**                                                                                                                                                                                                                     | `verifyRegistryChecksum` recomputes from the immutable entries and compares to the stored value; surfaced in `/admin/operations`'s "Registry health" section and the `registry:checksum:verify` CLI command. A mismatch would indicate either an algorithm change or (far more seriously) tampered entries — investigated as a security incident, not silently accepted.                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Concurrent activation          | **Fixed this phase**                                                                                                                                                                                                               | `publishRegistryVersion`/`rollbackRegistryVersion` are single `db.batch()` calls; combined with the existing partial-unique index (`idx_registry_versions_single_active`, migration 0009) enforcing at most one active release at the DB level, two concurrent activation requests cannot both succeed in creating two active releases — the second batch's `UPDATE ... WHERE is_active=true` targets whatever the first batch already left behind, converging to a single consistent state either way. Not covered by a dedicated concurrency test this phase (D1's single-writer-per-request model in the Miniflare test harness makes true concurrent-request races hard to simulate deterministically) — the DB-level invariant is the real safety net, verified structurally rather than by a race test. |
| No-active-release state        | **Fixed this phase**                                                                                                                                                                                                               | The old two-sequential-`UPDATE` pattern had a real window where zero releases were active if the process failed between statements. The new `db.batch()` makes this atomic.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Two-active-release state       | **Prevented at the DB level**                                                                                                                                                                                                      | `idx_registry_versions_single_active` (pre-existing, migration 0009) makes this a constraint violation, not just an application-logic hope.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Rollback without re-evaluation | **Fixed this phase**                                                                                                                                                                                                               | Previously true — rollback only moved the pointer. Now computes the same semantic diff and schedules the same re-evaluation as forward publish.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Re-evaluation storm            | **Mitigated by design**                                                                                                                                                                                                            | Re-evaluation never synchronously scans anything — it only moves `nextScanAt` into the past, and the existing bounded/rate-limited monitoring sweep (Phase 11) processes it on its normal cadence. No new unbounded work was introduced.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Notification storm             | **Mitigated by design**                                                                                                                                                                                                            | Re-evaluation doesn't itself send notifications — a resulting scan feeds the existing Phase 8 attribution → Phase 10 notification pipeline exactly like any other scan, with the same existing dedup/fatigue controls, unmodified by this phase.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Source content XSS             | **Not applicable this phase** — no source content is ever fetched or rendered (see scope note).                                                                                                                                    |
| Release-note XSS               | **Mitigated**                                                                                                                                                                                                                      | Release notes (`registry_versions.changelog`) are plain-text `zod` strings, rendered through the same React/Astro JSX escaping every other user-supplied string in this codebase goes through — no `dangerouslySetInnerHTML`/raw-HTML rendering path exists for changelog text (grepped, confirmed).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Public draft leakage           | **Mitigated**                                                                                                                                                                                                                      | The public crawler directory and `/changelog` are statically generated from the Markdown content collection, never from `registry_versions`/`registry_version_entries` directly — an unpublished draft release cannot leak through a surface that doesn't read from the registry tables at all (see `docs/registry/PUBLIC_REGISTRY_RENDERING_ARCHITECTURE.md`).                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Seed bypass                    | **Mitigated**                                                                                                                                                                                                                      | `reference-data.sql` uses `INSERT OR IGNORE` — re-running it never overwrites an existing `crawlers`/`registry_versions`/`registry_version_entries` row, and it never touches `is_active`. A production database that already has a published, active release is unaffected by re-running the seed (see `docs/registry/REGISTRY_CORRECTION_WORKFLOW.md`'s "what never happens").                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Admin account compromise       | **Out of scope, pre-existing controls apply**                                                                                                                                                                                      | Every registry-mutating route already requires `requireAdminAction` (Super Admin role + recent session + audited reason), unchanged by this phase — the same protection every other Admin mutation in this codebase relies on.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Historical scan corruption     | **Fixed this phase**                                                                                                                                                                                                               | The core bug this phase fixes: historical scan rendering (`getScanReport`, `domain-timeline.ts`) now resolves crawler identity from the scan's own recorded `registryVersionId` snapshot, not a live join — verified by `registry-reproducibility.integration.test.ts`'s second test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Live-row/snapshot mismatch     | **Fixed this phase** — this is the headline finding of the whole phase; see `docs/registry/PHASE_15_REGISTRY_BASELINE.md`.                                                                                                         |

## Admin registry security tests

`apps/web/tests/integration/admin-registry.integration.test.ts` already covers 403-for-non-admin.
This phase adds `apps/web/tests/integration/registry-security.integration.test.ts` covering IDOR
(publishing/rolling back a version ID belonging to no release, or malformed), IDOR against another
tenant's data is not applicable here (registry data has no per-tenant ownership), and replay
(re-submitting an identical publish/rollback request is verified idempotent by the same
concurrency-safety mechanism above).
