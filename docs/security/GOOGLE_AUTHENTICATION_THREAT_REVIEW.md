# Google Authentication Threat Review

Companion to [ADR-0009](../architecture/adr/ADR-0009-GOOGLE-FEDERATED-AUTHENTICATION.md) and
[AUTHENTICATION_SECURITY.md](./AUTHENTICATION_SECURITY.md). Written alongside the initial
implementation (2026-09-07); status is **implemented-local** — see
`docs/status/CURRENT_STATE.md` for what has and hasn't been verified against a live deployment.
Code references are relative to `apps/web/src/lib/auth/` unless noted.

| Threat                                                           | Mitigation                                                                                                                                                                                                                                                                                                                     | Residual risk                                                                                                                      |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Google token forgery                                             | `google.ts`'s `verifyGoogleIdToken` verifies the JWT signature against Google's real JWKS (`https://www.googleapis.com/oauth2/v3/certs`) via `jose`; a forged/unsigned/tampered token fails signature verification and is rejected before any account resolution runs.                                                         | None known — this is standard, cryptographically sound JWT verification, not decode-and-trust.                                     |
| JWT algorithm confusion                                          | `jwtVerify` is called with `algorithms: ["RS256"]` explicitly — an attacker cannot force HS256-with-public-key-as-secret or `alg: none` verification.                                                                                                                                                                          | None known.                                                                                                                        |
| JWKS/key rotation                                                | `jose`'s `createRemoteJWKSet` handles key rotation itself (re-fetches on an unrecognized `kid`, caches otherwise) — never a hand-rolled key cache.                                                                                                                                                                             | Relies on `jose`'s own caching correctness; `jose` is a widely used, actively maintained library, not custom code.                 |
| Wrong audience                                                   | `audience: expectedClientId` (the configured `GOOGLE_CLIENT_ID`) is enforced by `jwtVerify`; a token minted for a different Google OAuth client is rejected. `azp`, when present, is independently checked to match too.                                                                                                       | None known.                                                                                                                        |
| Wrong issuer                                                     | `issuer` restricted to Google's two documented values (`accounts.google.com`, `https://accounts.google.com`).                                                                                                                                                                                                                  | None known.                                                                                                                        |
| Expired token                                                    | `jwtVerify` enforces `exp` with a 5-second clock-tolerance, not a broad window.                                                                                                                                                                                                                                                | None known.                                                                                                                        |
| Nonce replay                                                     | Every OAuth intent (`oauth-intent.ts`) carries a fresh, cryptographically random nonce whose SHA-256 hash is stored; the callback hashes the token's `nonce` claim and compares it to the specific intent's stored hash, so a token minted for one ceremony cannot be replayed against a different intent.                     | None known — the nonce is bound 1:1 to the `state`-identified intent, not compared against a global/session-wide value.            |
| State replay                                                     | `consumeOAuthIntent` atomically marks a `state` consumed in the same conditional `UPDATE` that looks it up (`WHERE consumed_at IS NULL AND expires_at > now`) — a second use of the same `state`, concurrent or sequential, matches zero rows and fails closed.                                                                | None known — this is a single SQL statement, not a check-then-update race.                                                         |
| CSRF (the callback itself)                                       | Google's own `g_csrf_token` double-submit cookie is verified (cookie value === form field value, both non-empty) before anything else runs. This is the intentional, narrowly-scoped exception to `requireSession`'s same-origin Origin/Referer check (`google/index.ts`'s doc comment explains why).                          | The exception is scoped to exactly this one route; every other endpoint keeps the unmodified Origin/Referer check.                 |
| Login CSRF (forcing a victim into the attacker's Google account) | The one-time `state`/`nonce` pair is minted server-side per visitor session/page-load and is unguessable; an attacker cannot pre-supply a victim's browser with a `state` value that resolves to the attacker's own intended redirect/session outcome without also controlling the original `/api/auth/google/begin` response. | Standard OAuth/OIDC login-CSRF mitigation via server-issued, one-time, bound state — not a novel gap introduced by this design.    |
| Account linking attack                                           | Linking requires an authenticated session with recent-authentication step-up; `userId` is always derived server-side from that session, never the request body or the `state`/`nonce`. The callback re-derives and re-validates the session from the request's own cookie before completing a link.                            | None known.                                                                                                                        |
| Email-based account takeover                                     | Email is never used for authorization or linking — only Google's `sub`. See ADR-0009 and `google-account.ts`'s doc comment.                                                                                                                                                                                                    | None — this class of attack has no foothold in this design by construction.                                                        |
| Duplicate account creation                                       | `resolveOrCreateGoogleSignUp` checks for an existing link first; the `users`+`oauth_accounts` insert is one atomic `db.batch()`; a concurrent duplicate loses the `UNIQUE (provider, provider_subject)` race and falls back to resolving the winner's account rather than erroring or duplicating.                             | None known.                                                                                                                        |
| OAuth identity collision (`sub` already linked elsewhere)        | `linkGoogleAccount` rejects with `linked_elsewhere` without disclosing which account it belongs to.                                                                                                                                                                                                                            | None known.                                                                                                                        |
| Session fixation                                                 | Every successful Google authentication calls `createSession` fresh — it never reuses an anonymous or pre-existing session ID (ADR-0004's existing session model, unchanged).                                                                                                                                                   | None known.                                                                                                                        |
| Unsafe redirect                                                  | Every `redirectTo`/`failureRedirect` is validated with the existing `isSafeRelativeRedirect` at intent-creation time and stored server-side on the intent row — the callback never trusts a redirect target supplied by Google or the request; it only ever reads the value it itself wrote minutes earlier.                   | None known — same mechanism the existing passkey/audit-continuation flow already relies on (Phase 5).                              |
| Admin privilege escalation                                       | `resolveGoogleSignIn`/`resolveOrCreateGoogleSignUp`/`linkGoogleAccount` all independently check `isAdminAccount` and refuse outright; Google authentication never computes `isAdminSession` from the resolved user — it is hardcoded `false`, unlike passkey login/finish.ts, which does compute it.                           | None known — this is a stronger posture than "just don't set the flag": the account is never authenticated via Google at all.      |
| Provider-token leakage                                           | No Google ID/access/refresh token is ever persisted to a table, written to a log, included in an API response, or sent to analytics — only the verified `sub`/email/name are extracted in-memory and never round-tripped.                                                                                                      | None known.                                                                                                                        |
| Logs/analytics leakage                                           | `security_events.details` for Google failures carries only a small controlled `reason` string (e.g. `google_csrf_mismatch`) — never the token, state, or nonce. `trackEvent`'s existing `PROHIBITED_PROPERTY_KEY_PATTERN` guard is untouched; no Google claim is ever passed as an analytics property.                         | None known.                                                                                                                        |
| Google script compromise surface                                 | The GIS script is loaded only on `/sign-in` and the account-settings page (not site-wide); a script/network failure disables only the Google UI (`googleUnavailable`) and never blocks passkey/recovery sign-in (section 32).                                                                                                  | Accepted, standard third-party-script supply-chain risk — same category as Paddle.js, already accepted elsewhere in this codebase. |
| CSP expansion                                                    | Only Google's own documented GIS origins (`accounts.google.com/gsi/*`) were added to `script-src`/`style-src`/`frame-src`/`connect-src` — no broad `*.google.com`/`https:` shortcut, `object-src`/`base-uri`/`frame-ancestors`/`form-action` unchanged. See `security-headers.test.ts`.                                        | None known.                                                                                                                        |
| Lockout after unlink                                             | `disconnectGoogleAccount` refuses (`lockout_risk`) unless the account has at least one active passkey — recovery codes deliberately don't count (section 24's explicit instruction).                                                                                                                                           | None known.                                                                                                                        |
| Account deletion                                                 | `oauth_accounts`/`oauth_auth_intents` both carry `ON DELETE CASCADE` on `user_id` (migration 0038) — the existing final-purge job (`data-retention.ts`'s `purgeDeletedAccounts`) removes them automatically the same way it removes every other owned row, with no separate code path to keep in sync.                         | None known.                                                                                                                        |
| Suspended account re-entry                                       | `resolveGoogleSignIn` blocks `status === "suspended"` exactly like passkey `login/finish.ts`; `pending_deletion` accounts can still authenticate via Google, matching the existing cancellable-deletion semantics.                                                                                                             | None known — intentionally identical policy to the existing passkey path, not a new decision.                                      |
| Race conditions (concurrent duplicate signup/link)               | Covered by the atomicity notes above (`db.batch()` for signup, `UNIQUE` constraints + catch-and-resolve for both signup and link) — the DB constraint is the final authority, not application-level check-then-write.                                                                                                          | None known.                                                                                                                        |

## Known limitation: this review is not yet backed by live evidence

This document was written alongside the code, before any deployment. It records the intended
design and the reasoning behind it, verified by unit/integration tests against a real (Miniflare)
D1 database and real cryptographic JWT verification (locally generated test keys) — **not** by
observing the real Google network, a real preview deployment, or a real production account. See
`docs/status/CURRENT_STATE.md` for exactly what has and hasn't been exercised, and
`docs/deployment/GOOGLE_AUTHENTICATION_DEPLOYMENT_CHECKLIST.md` for the remaining owner/deployment
steps before any of the above should be treated as verified against the real system.
