infrastructure built this phase (migration `0036`, `apps/web/src/lib/admin/pilots.ts`,
`apps/web/src/lib/admin/pilot-analytics.ts`, the `/admin/pilots` workspace, and
`/api/app/pilot/feedback`) against §103/§130's threat checklist.

## Additional checks performed

- **SSRF / arbitrary fetch**: none of this phase's code makes an outbound HTTP request of any
  kind — it is pure D1 read/write plus existing internal-note/session helpers. Nothing to review
  here.
- **CSRF**: covered by the existing `assertSameOrigin` check inside `requireSession`/
  `requireAdminSession` for every new route — no new CSRF surface introduced.
- **D1/Worker CPU exhaustion**: `getPilotCohortMetrics` bounds its queries to the specific
  cohort's participant `user_id`s via `inArray`, never scans `product_events`/`domains` globally.
  See `docs/data/PHASE_17_PILOT_QUERY_AND_INDEX_AUDIT.md` for `EXPLAIN QUERY PLAN` evidence.
- **Account-deletion interaction**: FK cascade design reviewed in
  `docs/pilot/PHASE_17_PILOT_DATA_MODEL_DECISION.md` — a pilot participant row can never block
  the existing `purgeDeletedAccounts` hard-delete.

## Findings requiring a fix

None. No P0/P1 issue was found in this review.
