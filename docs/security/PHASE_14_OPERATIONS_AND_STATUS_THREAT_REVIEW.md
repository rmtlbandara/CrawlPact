# Phase 14 Operations and Status Threat Review

**Level 4 document.** Reviews the status/operations/incident/alerting architecture this phase
touched or built.

| Threat                                     | Assessment | Evidence                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------ | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public internal-detail leak                | Low        | `PublicIncident`/`PublicComponentStatus` (`lib/status/public-status.ts`) are distinct TypeScript types from the internal `ComponentHealth`/`OperationalAlertRow` types — a compile-time boundary, not just a runtime filter. See `docs/operations/PUBLIC_INTERNAL_STATUS_BOUNDARY.md` "Enforcement".                  |
| Public customer-data leak                  | Low        | No customer domain, account ID, or email appears anywhere in `PublicStatusReport`/the Atom feed's output shape — verified by reading every field on both types.                                                                                                                                                       |
| False Operational state                    | Low        | `getPublicStatus()`'s `catch` sets `status_unavailable`, never a default "operational" — pre-existing, re-verified this phase, and this phase's own new failure paths (`getOperationsSummary`, `evaluateOperationalAlerts`) never write to the public status computation at all.                                      |
| Incident stored XSS                        | Low        | Astro templates auto-escape all incident-derived text (`status.astro` has zero `set:html` usage, grepped); admin incident text is length-bounded (title ≤200, summary/message ≤2000) at the Zod schema layer (`api/admin/incidents/index.ts`).                                                                        |
| Admin incident CSRF                        | Low        | Every admin incident/operations route goes through `requireAdminSession`/`requireAdminAction`, both of which chain through `requireSession`'s Origin/Referer same-site check (`lib/auth/require-session.ts`) — the same protection `csrf.integration.test.ts` already verifies.                                       |
| Incident IDOR                              | Low        | Single-tenant admin surface — `listIncidents`/`addIncidentUpdate` require an authenticated Super Admin session; there is no per-customer incident scoping to bypass.                                                                                                                                                  |
| Operational alert IDOR                     | Low        | Same reasoning — `operational_alerts` has no customer scoping at all (it is a system-wide internal table); `acknowledgeOperationalAlert` requires `requireAdminAction`.                                                                                                                                               |
| Status cache poisoning                     | Low        | `/status`'s `Cache-Control: public, max-age=30` output is not cookie/user-varying (no `Vary` on session state) — identical output for every visitor, so there is no cache-key confusion vector to poison.                                                                                                             |
| Stale status                               | Low        | 30-second cache TTL, unchanged this phase; incident state changes are visible within that window.                                                                                                                                                                                                                     |
| Status DB failure                          | Low        | Covered by "False Operational state" above — `status_unavailable`, not a silent fallback.                                                                                                                                                                                                                             |
| Public feed XML injection                  | Low        | The new `/status/feed.xml` (`apps/web/src/pages/status/feed.xml.ts`) escapes every incident-derived string via a dedicated `escapeXml()` helper before interpolation — see the route's own tests.                                                                                                                     |
| Malicious incident link                    | Low        | No incident field is ever rendered as an `href`/`src` attribute anywhere in `status.astro` or the new Atom feed (grepped, zero matches) — incident text is plain text content only.                                                                                                                                   |
| Maintenance-mode abuse                     | Low        | Toggling `maintenance_mode`/`scheduler_paused` requires `requireAdminAction` (reason + step-up auth + audit log), same as every other high-impact runtime-config key (`HIGH_IMPACT_KEYS`, `lib/admin/runtime-config.ts`).                                                                                             |
| Destructive admin operation                | Low        | No one-click destructive action was added this phase — `retention-dry-run` is always dry-run (never deletes), `evaluate`/`reconcile-notifications` are read/idempotent-repair only, `acknowledge` only sets a timestamp.                                                                                              |
| Recovery-operation abuse                   | Low        | Same reasoning — no recovery/purge action added this phase can itself destroy data; a real D1 Time Travel restore (the only genuinely destructive recovery action in scope) was not built as an in-app action at all, and remains a manual, explicitly-approved-only Cloudflare-side operation.                       |
| Status spoofing                            | Low        | No externally-supplied input feeds `getPublicStatus()`'s computation — every input is either internal D1 state or admin-authored incident content, itself already covered above.                                                                                                                                      |
| Operational log secret leak                | Low        | `worker.ts`'s new `evaluateOperationalAlerts(...).catch((error) => console.error(...))` logs only the thrown error object — the same pattern every other job in this file already uses; no secret material is constructed or passed through this path.                                                                |
| Health endpoint information disclosure     | N/A        | No public `/health` endpoint was added this phase (§114's own guidance: a rich public health endpoint should not exist) — the only health data exposed is `/status`'s already-reviewed public output.                                                                                                                 |
| Status snapshot tampering                  | N/A        | No separate status snapshot store exists — Option A was chosen (`docs/operations/PHASE_14_INDEPENDENT_STATUS_PLANE_DECISION.md`); `getPublicStatus()` is computed fresh from D1 on every request, with no intermediate cache an attacker could tamper with beyond Cloudflare's own edge cache (unchanged this phase). |
| Independent status Worker misconfiguration | N/A        | No independent status Worker was built this phase.                                                                                                                                                                                                                                                                    |
| Public/private analytics regression        | Low        | `pnpm analytics:validate` (Phase 13) was re-run against this phase's full changeset and still passes — no GA reference was added to `/status`, `/status/feed.xml`, `/admin/operations`, or any new file.                                                                                                              |

## Residual, disclosed limitations

- The D1 Time Travel restore capability was verified live (a real bookmark retrieved from the
  preview database) but a full restore-and-verify cycle was not executed — see
  `docs/operations/PHASE_14_RELIABILITY_GAME_DAY.md`. This is an operational-readiness gap, not a
  security vulnerability: the capability exists and was proven reachable; only the end-to-end drill
  itself remains unexecuted, by the same "requires separate explicit approval" reasoning applied in
  Phase 11.
- `security_events`/`notifications` retention remains open (RISK-006, partial) — a privacy-adjacent
  gap already tracked as a named risk, not newly discovered by this review.
