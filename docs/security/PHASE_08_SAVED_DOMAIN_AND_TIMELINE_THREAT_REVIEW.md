# Phase 8 — Saved-Domain and Timeline Threat Review

## Scope

Every new/changed surface in this phase: `domain_change_events` (materialised timeline),
`findings.fingerprint`, `domains.scan_lock_until`, the three new API routes
(`/api/domains/:domainId/timeline`, `/scans`, `/compare/:previousScanId/:currentScanId`), the
comparison page, the redesigned domain list/detail pages, and the `establishBaseline`/
`updateDomain`/`monitoring.ts`/`scan.ts` timeline-generation call sites.

## Threats reviewed

| Threat                                                                                 | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                  | Evidence                                                                                                                                                                                         |
| -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Cross-account domain access                                                            | Every route resolves the domain via `getOwnedDomain(db, user.id, domainId)` first — scoped by `ownerUserId` and `isNull(deletedAt)` — before any timeline/scan/comparison query runs. A nonexistent or unowned domain returns the same `NOT_FOUND` either way.                                                                                                                                              | `domain-timeline-api.integration.test.ts` — 404 for a stranger's domain on all three new routes.                                                                                                 |
| Cross-account scan access                                                              | `compareScans()` independently re-checks `scan.domainId === domainId` for **both** scan IDs, not just the domain-level check — a scan ID from another account (even a real one) can never be substituted into a request for a domain you own.                                                                                                                                                               | `domain-change-timeline.integration.test.ts` — "rejects a comparison against a scan belonging to a different domain".                                                                            |
| Cross-account timeline/comparison access as an existence oracle                        | Both the "domain not found" and "scans not comparable" paths return the same shape/status a genuinely made-up ID would — no distinct error reveals "this ID exists but isn't yours" vs. "this ID doesn't exist".                                                                                                                                                                                            | Code review of `compareScans()`'s `!previousScan \|\| previousScan.domainId !== domainId` branch (identical handling for both cases); `domain-timeline-api.integration.test.ts`.                 |
| Timeline-event tampering                                                               | Every `domain_change_events` row is written server-side only, from `generateTimelineEvent()`/`generatePresetChangeEvent()` — no API route accepts a client-supplied event field. No update path exists for this table at all (rows are immutable once inserted).                                                                                                                                            | Code review: no `PATCH`/`PUT` route touches `domain_change_events`.                                                                                                                              |
| Event duplication (retry/replay)                                                       | A unique index on `fingerprint` plus `onConflictDoNothing()` — a retried scheduled sweep, a raced manual/scheduled scan pair, or a duplicate preset-change call all resolve to the same single row.                                                                                                                                                                                                         | `domain-change-timeline.integration.test.ts` — "is idempotent" (scan comparison) and "is idempotent within the same minute" (preset change).                                                     |
| Event replay (an attacker resubmitting an old request to force a fake "current" event) | Every event's `observedAt`/`current_scan_id` is derived server-side from the real scan row being processed at generation time — there is no client-suppliable timestamp or event payload for this table.                                                                                                                                                                                                    | Code review of `generateTimelineEvent()`'s signature (`domainId`, `previousScanId`, `currentScanId` only — no summary/origin/attention-level parameter).                                         |
| Diff-attribution manipulation                                                          | `computeChangeOrigin()` reads only `scans`/`scan_resources` rows already written by the trusted `persistScan()` path — no request parameter influences the attribution decision.                                                                                                                                                                                                                            | Code review of `change-attribution.ts`'s signature (two scan IDs only).                                                                                                                          |
| Stored XSS via scan evidence                                                           | All `scan_resources.snapshotText` is rendered through JSX text nodes (React's default escaping) in the comparison page and timeline — no `dangerouslySetInnerHTML` anywhere in this phase's new components.                                                                                                                                                                                                 | `saved-domain-timeline.spec.ts` — "evidence renders as inert text (no raw HTML)"; code review of every new `.tsx`/`.astro` file (grep confirms zero `dangerouslySetInnerHTML`/`set:html` usage). |
| Evidence injection into script/style context                                           | Evidence is only ever interpolated into `<pre>`/text-node positions, never into an inline `<script>` block or attribute the way `resource_hash` mismatches could otherwise be exploited.                                                                                                                                                                                                                    | Code review.                                                                                                                                                                                     |
| CSRF                                                                                   | Every mutating route (`POST /scan`, `PATCH /:domainId`) already goes through `requireSession()`'s existing same-origin check (unchanged by this phase); the three new routes added in this phase are all `GET`-only (read paths), so CSRF does not apply to them.                                                                                                                                           | Existing `requireSession()` coverage, confirmed unchanged.                                                                                                                                       |
| Manual-rescan abuse / duplicate simultaneous scans                                     | New `domains.scan_lock_until` claim (`tryClaimScanLock`), a conditional UPDATE matching the existing scheduled-sweep claim pattern — a second concurrent request for the same domain is rejected with `SCAN_ALREADY_RUNNING` (409) before it can consume quota or trigger a second `runAudit`. The scheduled sweep's own `claimDueDomains` was extended to skip a domain currently locked by a manual scan. | `domain-change-timeline.integration.test.ts` — "prevents a second concurrent claim until released".                                                                                              |
| Monitoring-toggle abuse                                                                | Unchanged from the existing `PATCH /api/domains/:domainId` authorisation (ownership-scoped, ratified by this phase's `updateDomain()` extension only adding a _read_ of the existing row before the update, no new privilege).                                                                                                                                                                              | Code review.                                                                                                                                                                                     |
| Quota bypass                                                                           | The manual-rescan quota check (`countManualScansThisMonth`) is unchanged; the new scan-lock sits _in addition to_ it, not instead of it — a lock rejection happens without ever incrementing/consuming the quota (no `scans` row is written for a rejected request).                                                                                                                                        | `scan.ts` code review; existing `AUDIT_QUOTA_EXCEEDED` test still passes unmodified.                                                                                                             |
| History-retention bypass                                                               | `retentionBoundaryFor()` and the scan-history/timeline list queries only ever read rows that still physically exist in D1 — there is no separate "hidden" retained-data path this phase could bypass; retention enforcement itself (`purgeExpiredDomainScans`) is unchanged Phase 11 code.                                                                                                                  | Code review — no new retention-bypass surface introduced.                                                                                                                                        |
| Private-cache leak                                                                     | No route in this phase sets an explicit `Cache-Control` header, so the global middleware default (`private, no-store`) applies to every one of them, same as every other authenticated route in this codebase.                                                                                                                                                                                              | Code review of `middleware.ts` (unchanged) plus the absence of any `Cache-Control` override in the new route files.                                                                              |
| Shared-report escalation                                                               | The comparison/timeline pages are never reachable through a report's private-share token — `sharing.ts`'s `getShareForToken()` resolves only a single scan's report, with no domain-scoped fan-out to timeline/scan-history/comparison data.                                                                                                                                                                | Code review — no code path connects a share token to `domain_change_events`/`scan-history.ts`/`domain-comparison.ts`.                                                                            |
| Deleted-domain race                                                                    | `domain_change_events.domain_id` has `ON DELETE CASCADE` — a domain deletion mid-request either completes before or after any in-flight timeline read/write; there is no window where an orphaned event referencing a deleted domain could be returned (the FK guarantees it, not application-level timing).                                                                                                | Migration 0026 `ON DELETE CASCADE`; matches the existing `scan_diffs` pattern.                                                                                                                   |
| Scan-retention race (a scan purged mid-comparison)                                     | `previous_scan_id`/`current_scan_id` are `ON DELETE SET NULL` — a scan purged between the timeline listing and a comparison request degrades gracefully (`compareScans()` returns `not found`/`incompatible`, never a crash or stale-data leak).                                                                                                                                                            | Migration 0026; `compareScans()`'s explicit `!previousScan` branch.                                                                                                                              |
| Registry-version deletion impact                                                       | Registry versions are never actually deleted in this codebase (only unpublished via `isActive`) — the defensive `ON DELETE SET NULL` on `domain_change_events.previous/current_registry_version_id` is therefore untested against a real deletion today, but matches this phase's own retention-compatibility rule for if that ever changes.                                                                | Migration 0026; documented limitation.                                                                                                                                                           |
| Pagination abuse (requesting an unbounded page)                                        | `listDomainChangeEvents`/`listScanHistory` clamp `limit` to `[1, 50]` server-side regardless of what a caller requests.                                                                                                                                                                                                                                                                                     | Code review of `Math.min(Math.max(options.limit ?? 20, 1), 50)` in both functions.                                                                                                               |
| Unbounded evidence loading                                                             | Comparison evidence is loaded only for the two specific scan IDs in the URL, per comparable resource type (max 7 types) — never a full-history evidence dump.                                                                                                                                                                                                                                               | Code review of `compareScans()`.                                                                                                                                                                 |
| Filter/query injection                                                                 | The scan-history `filter` query parameter is validated against a fixed allow-list (`VALID_FILTERS`) before use; any unrecognised value silently falls back to `"all"` rather than being interpolated into SQL. Every other query parameter goes through Drizzle's parameterised query builder, never raw string concatenation.                                                                              | Code review of `scans.ts`'s `VALID_FILTERS` check.                                                                                                                                               |
| Operational error leakage                                                              | No new route in this phase changes the existing `jsonErrorResponse()` error-mapping convention — an unexpected internal error still returns a generic `INTERNAL_ERROR` envelope, never a raw stack trace or D1 error message.                                                                                                                                                                               | Existing `json-response.ts`, unchanged.                                                                                                                                                          |

## Tests added for this review

`domain-change-timeline.integration.test.ts` (24 tests) and `domain-timeline-api.integration.test.ts`
(8 tests) directly exercise the IDOR, idempotency, scan-lock, and pagination rows in the table
above against real D1. `saved-domain-timeline.spec.ts` exercises the XSS-escaping row in a real
browser. See the completion report for the full command/result evidence.
