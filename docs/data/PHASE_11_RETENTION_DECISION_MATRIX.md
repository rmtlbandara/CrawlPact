# Phase 11 retention decision matrix

Stage 11D. Classifies every data category the Phase 11 prompt named (`product_events`,
`security_events`, `notifications`, `webhook_events`, `transactions`, `admin_audit_logs`,
shared-report access logs, temporary continuation records, operational performance samples, R2
orphans) against real code — not assumption — and records what is enforced, what is intentionally
left unbounded and why, and what remains a genuinely open decision this phase does not have the
authority to close on its own.

**Scope boundary respected**: the Phase 11 prompt instructs "implement only approved retention
periods." The SRS's own retention table (§34) is explicitly labelled **"Recommended retention"**
and has no line item for `product_events`, `security_events`, or `notifications` specifically —
only "Administrative logs: at least 24 months" and "Billing reconciliation records: as legally and
operationally required." Per `CLAUDE.md`'s "never silently reinterpret an SRS requirement" rule,
this phase does not invent a retention number for a category the SRS is silent on and call it
implemented. Categories in that position are recorded below with a _recommendation_, not a
decision — RISK-006 stays open until a human explicitly approves (or explicitly accepts leaving
unbounded, which its own acceptance criteria also permits).

## Method

Every category was checked against the real schema (`packages/database/src/schema/`) and the real
purge job (`apps/web/src/lib/data-retention.ts`) — not the SRS's aspirational table alone — to
confirm what's actually enforced today, not what was intended.

## Recommendation for the three open categories (not yet approved)

For `product_events`, `security_events`, and `notifications`, a reasonable, evidence-based
recommendation — **for a human to approve, not something this phase implements unilaterally**:

- **`product_events`**: 18 months. Long enough for year-over-year product/cohort analysis, short
  enough to bound growth. Lowest sensitivity of the three (aggregate usage metrics, already
  severed from a deleted user via `SET NULL` per the Stage 11B audit).
- **`security_events`**: 24 months, matching the SRS's explicit "administrative logs" floor —
  treating it as the same class of record (a security-relevant audit trail) rather than inventing
  a separate number.
- **`notifications`**: 90 days after `read_at` is set (or from creation if never read). These are
  transient in-app UI state, not an audit or compliance record — the shortest-retention category
  of the three by a wide margin.

These numbers are a starting proposal only. Implementing a purge job for any of them without
explicit approval would violate this phase's own scope boundary — see
`docs/risks/ACTIVE_RISKS.md` RISK-006, left at **status: monitoring** (not closed) pending that
approval.

## What this phase changed as a direct result of this matrix

- Confirmed `audit_continuations` needed (and now has) its own purge step — found during the
  Stage 11B FK audit, not originally in RISK-006's list, but the same "unbounded record" class of
  problem.
- Confirmed no new purge job is owed for `admin_audit_logs`, `transactions`, or `webhook_events` —
  their current "kept indefinitely" treatment already matches the SRS's own wording, not a gap.
- Confirmed the "shared-report access logs" and "operational performance samples" categories named
  in the Phase 11 prompt don't correspond to anything that exists in this codebase — recorded here
  rather than silently ignored, so a future author doesn't go looking for a table that was never
  built.
