# Phase 11 foreign-key and deletion audit

Stage 11B. Every foreign key below was read directly from the live production database via
`PRAGMA foreign_key_list(<table>)` (Cloudflare MCP, read-only), not inferred from migration
history — migration files are historical/append-only in this repo (ADR-0002), so the _current_
authoritative shape of a rebuilt table can only be confirmed by reading the real, current schema,
not by re-deriving it from whichever migration last touched it. This is the same discipline
`docs/data/DATA_RETENTION.md`'s "Part 3 Step 21" section already established for the 14
actor-reference columns fixed in migrations 0013–0015.

## Method

For every table with a foreign key touching `users`, `domains`, `scans`, `shared_reports`,
`billing_customers`, or `subscriptions` — the six "root" tables whose rows are ever actually
deleted or expired by real code paths (account deletion, scan retention, share revocation) — this
audit records the real `on_delete` behaviour and classifies it as one of:

- **Correct as-is** — the behaviour matches what the record's own lifecycle requires.
- **Fixed this phase** — a real, evidenced problem, corrected via a migration in this PR.
- **Latent, not currently triggered** — a real gap by the same reasoning as the fixed ones, but no
  code path in this repository currently deletes the parent row it depends on, so it cannot fire
  today. Recorded, not fixed, per the phase's own "do not change correct relationships merely for
  consistency" instruction — fixing something nothing can trigger yet is speculative work, not
  hardening.

## Why the "latent" findings are not fixed this phase

The phase's own migration-authoring guidance is explicit: _"Do not change correct relationships
merely for consistency"_ and _"Review every foreign key... Create [this audit]"_ — the audit itself
is the required deliverable for the billing-adjacent columns above, not a mandate to pre-emptively
migrate every table whose behaviour would matter only if a not-yet-built feature is added. Each
latent finding above is recorded with enough detail (exact column, exact current behaviour, exact
condition that would make it fire) that a future change adding real `billing_customers`/
`subscriptions` deletion does not have to rediscover this from scratch — it can be fixed in the
same PR that introduces the trigger, which is the point at which the correct target behaviour
(`SET NULL`? `RESTRICT`? a soft-delete instead?) can actually be decided with real product
context, rather than guessed at now.

## What this audit does not cover

Reference/registry tables (`crawlers`, `registry_versions`, `ruleset_versions`,
`crawler_operators`, `registry_version_entries`) were excluded — their rows are never deleted by
any retention or account-deletion path (they're an editorial, admin-curated dataset, per
`docs/registry/CRAWLER_REGISTRY_GOVERNANCE.md`'s immutability rules), so no FK-on-delete question
applies to them in practice. `admin_role_assignments`, `runtime_configuration`, `system_notices`
were already fixed in migration `0015` and re-confirmed unchanged during this audit's `PRAGMA`
sweep — not re-tabulated above to avoid duplicating that migration's own documentation.
