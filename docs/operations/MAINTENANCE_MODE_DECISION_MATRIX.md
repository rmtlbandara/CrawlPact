# Maintenance Mode Decision Matrix

**Level 2 document.** Phase 14 (§45-46). Audits the existing `maintenance_mode` runtime-config flag
(SRS §28.17) against precise containment per maintenance type, rather than one indiscriminate
"everything off" switch. **Finding: the existing implementation already matches precise
containment** — no code change was needed, this document records the audit evidence.

## What remains available while `maintenance_mode = true` (real, current behaviour)

| Concern                     | Behaviour                                                                                                                                                                                                                                                                           | Evidence                                                                                                         |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Public marketing site       | Fully accessible — the flag is never checked by any marketing-page route                                                                                                                                                                                                            | No `maintenance_mode` reference anywhere under `apps/web/src/pages/*.astro` outside `/app`/`/admin`/`/api/audit` |
| Authenticated product       | Read-only for mutating requests only — `require-session.ts`'s `requireAuthenticatedSession` throws `MAINTENANCE_MODE_ACTIVE` (503-equivalent) for any non-`SAFE_METHODS` request from a non-admin user; GET requests (viewing the dashboard, saved domains, history) are unaffected | `apps/web/src/lib/auth/require-session.ts:60-74`                                                                 |
| Super Admin access          | **Exempt** — administrators can still act (including turning maintenance mode back off) while it's active, since `require-session.ts`'s check only applies `&& !result.user.isAdmin`                                                                                                | Same file, same lines                                                                                            |
| Billing (checkout/webhooks) | Webhooks remain fully receivable — `POST /api/billing/webhook` has no `maintenance_mode` check at all; only new _authenticated_ billing actions (plan changes) are blocked via the same mutating-request gate as the rest of the dashboard                                          | `apps/web/src/pages/api/billing/webhook.ts` (grepped, zero matches for `maintenance`)                            |
| Background monitoring       | Independently pauses — `worker.ts`'s `scheduled()` checks `isMaintenanceMode(env.DB)` separately from the mutating-request gate and skips `runMonitoringJob`, recording an honest "Skipped: maintenance mode is active" `scheduled_job_runs` row rather than silently doing nothing | `apps/web/src/worker.ts`                                                                                         |
| New anonymous audits        | Paused — `POST /api/audit` returns `503 MAINTENANCE_MODE_ACTIVE` before running the registry lookup                                                                                                                                                                                 | `apps/web/src/pages/api/audit/index.ts:89-104`                                                                   |
| Data retention              | **Not gated** — `runRetentionJob` runs unconditionally regardless of maintenance mode, since it is a privacy/compliance job, not a scanning one (deliberate, matches the existing "retention runs unconditionally" rationale in `worker.ts`'s own doc comment)                      |
| Data corruption             | None possible from the flag itself — it only gates request handling, never touches stored data                                                                                                                                                                                      |
| User-facing message         | `"CrawlPact is in maintenance mode. The dashboard is temporarily read-only."` / `"...New audits are temporarily paused."` — specific per surface, not a generic error                                                                                                               | Same files as above                                                                                              |
| Admin recovery              | Always possible — admins are exempt from the gate itself, so turning the flag back off never requires a separate emergency bypass                                                                                                                                                   | `require-session.ts` admin exemption                                                                             |

## Per-maintenance-type mapping (§46)

| Maintenance type                                        | What's actually needed                                                                                                  | Current mechanism                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Application maintenance (a deploy, a config change)     | Dashboard read-only, audits paused, admins still working                                                                | `maintenance_mode` flag — already correct for this case                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Database maintenance (a migration, a D1-side operation) | Same as application maintenance — D1 is the only datastore, so there's no narrower "database-only" containment to build | `maintenance_mode` flag — same mechanism, appropriately reused (not a separate flag, since the underlying dependency is identical)                                                                                                                                                                                                                                                                                                                                                                       |
| Billing maintenance                                     | Checkout/webhook-specific containment                                                                                   | **No dedicated flag exists.** `BILLING_ENABLED=false` (an env var, not a runtime-toggleable admin setting) is the closest existing lever, but it disables billing entirely rather than putting it into a "temporarily paused, will resume" state. Not built this phase — real billing incidents to date have been handled via webhook retry (`/admin/webhooks`) and Paddle resync (`docs/operations/BACKUP_AND_RECOVERY.md`), not a maintenance-mode toggle. Disclosed gap, not silently assumed solved. |
| Scanner maintenance                                     | Pause new scans without blocking the rest of the product                                                                | `AUDIT_ENGINE_ENABLED=false` (env var) already does exactly this for the whole product, and `maintenance_mode` additionally pauses just new-audit creation without needing the engine fully disabled — see `docs/operations/DISASTER_RECOVERY_RUNBOOK.md` "Scanner"                                                                                                                                                                                                                                      |
| Security incident containment                           | Immediate, broad lockdown distinct from routine maintenance                                                             | `maintenance_mode` + `scheduler_paused` together cover "stop new customer-facing mutation and stop new scans," but neither revokes existing sessions or blocks read access — a genuine security-containment scenario (e.g. a compromised admin account) needs the separate, already-existing session/passkey revocation tooling (`/admin/users`), not this flag. See `docs/operations/DISASTER_RECOVERY_RUNBOOK.md` "Authentication".                                                                    |

## Conclusion

The existing single `maintenance_mode` flag already implements precise, per-surface containment
(read-only dashboard, paused audits, independent monitoring pause, unaffected public site,
unaffected billing webhooks, admin-exempt) rather than one indiscriminate "everything off" switch —
it satisfies §45's audit requirements without a code change. The one real, disclosed gap is billing
maintenance having no dedicated toggle narrower than `BILLING_ENABLED` — left open, not silently
assumed solved, since no real billing incident to date has needed it and building an unused
containment lever risks its own untested-in-anger failure mode.
