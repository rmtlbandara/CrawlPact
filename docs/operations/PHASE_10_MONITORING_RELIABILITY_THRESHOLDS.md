# Phase 10 — Monitoring Reliability Thresholds

Internal operational thresholds only — no external SLA is published (per §25, deliberately). All
metrics are exposed via `GET /api/admin/capacity` (`apps/web/src/lib/admin/capacity.ts`).

| Metric                            | Field                                                   | Warning                       | Critical                 | Basis                                                                                                                                                                                                                                                                                                                                  |
| --------------------------------- | ------------------------------------------------------- | ----------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Overdue monitoring backlog        | `monitoring.dueNowCount`                                | > 20 (one full default batch) | > 100                    | A backlog exceeding one sweep's batch size means it will take multiple daily ticks to clear                                                                                                                                                                                                                                            |
| Oldest overdue domain             | `monitoring.oldestOverdueNextScanAt`                    | > 48h past due                | > 7 days past due        | Beyond the daily-cron self-heal window (24h) means the scheduler itself is degraded                                                                                                                                                                                                                                                    |
| Long-overdue active domains       | `monitoring.longOverdueActiveDomainCount`               | > 0                           | > 10                     | Per `MONITORING_STATE_RECONCILIATION.md` — should structurally be 0; any nonzero value means the self-heal mechanism isn't keeping up                                                                                                                                                                                                  |
| Platform-side scan failures (24h) | `monitoring.platformFailureCountLast24h`                | > 5                           | > 20                     | A real CrawlPact-side defect, not target-side — measured against Phase 11's production baseline of near-zero                                                                                                                                                                                                                           |
| Target-side scan failures (24h)   | `monitoring.targetFailureCountLast24h`                  | —                             | —                        | Expected to fluctuate with real target uptime; not itself actionable without per-domain drill-down (already available via Admin Domains)                                                                                                                                                                                               |
| Paused domains                    | `monitoring.pausedDomainCount`                          | —                             | —                        | Informational — a customer-visible, expected outcome of repeated target failures, not itself a platform problem                                                                                                                                                                                                                        |
| Notification creation (24h)       | `notifications.createdLast24h`                          | —                             | —                        | Informational baseline; production has 0 notification rows as of the Phase 9 baseline, so early Phase 10 volume is expected to be near-zero                                                                                                                                                                                            |
| Reconciliation job status         | `notifications.reconciliationLastRun.status`            | `failed` once                 | `failed` 3 runs in a row | Uses the existing `scheduled_job_runs` status the retention/monitoring jobs already report through                                                                                                                                                                                                                                     |
| Scheduled-job failure (any)       | `scheduled_job_runs.status = 'failed'`                  | 1 occurrence                  | 3 consecutive            | Reuses `apps/web/src/lib/admin/scheduler.ts`'s existing `detectSchedulerAnomalies` (Phase 11), not duplicated here                                                                                                                                                                                                                     |
| Feed endpoint error anomaly       | —                                                       | —                             | —                        | Not separately measured — the feed route has no distinct error-rate metric; a spike would show as a general Worker error-rate anomaly in Cloudflare's own dashboard, out of this Worker's own measurable reach (see `docs/operations/PHASE_11_OPERATIONAL_CAPACITY_VIEW.md`'s precedent for what a Worker cannot measure about itself) |
| Auto-pause rate                   | derivable from `monitoring.pausedDomainCount` over time | —                             | —                        | No dedicated rate field added this phase; a time-series would require a new metrics table, not justified by current volume (near-zero production domains)                                                                                                                                                                              |

Thresholds are derived from Phase 11's real measured capacity (`MONITORING_CAPACITY_PLAN.md`'s
batch-size/CPU findings, `PHASE_11_PRODUCTION_CAPACITY_BASELINE.md`'s near-zero real volume), not
invented — at current near-zero production scale these thresholds are conservative headroom, not a
tight tripwire, and are expected to be revisited once real paid-customer volume exists.

## Public incidents

Crossing a threshold may prompt an internal operational response (investigate, and if warranted,
manually pause the scheduler via the existing `scheduler_paused` admin toggle). Phase 14 owns
whether/how a crossed threshold becomes a public status/incident communication — this document does
not attempt that.
